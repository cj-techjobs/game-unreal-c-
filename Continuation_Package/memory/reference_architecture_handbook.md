The target architecture for converting the SOTM Unreal project from Blueprint-only to a C++ foundation is specified in `Docs/Architecture/Architecture-Handbook.html` (source Markdown split across files like `01-Foundation-and-Code-Setup.md` in the same folder). It defines the 5-module structure (`SOTM1`, `SOTMCore`, `SOTMGameplay`, `SOTMPresentation`, `SOTMEditor`), the 12 framework classes and 9 subsystems, and an 11-milestone build order (M0-M11).

Live inspection/editing of the Unreal Editor itself (Blueprints, actors, levels, PIE sessions, logs) happens via Epic's official `ModelContextProtocol` ("Unreal MCP") plugin plus `AllToolsets`/`EditorToolset`, exposed over HTTP at `http://127.0.0.1:8000/mcp` (project-root `.mcp.json`), reachable through the `mcp__unreal-mcp__call_tool` / `list_toolsets` / `describe_toolset` tools. This requires the Unreal Editor to actually be open with the project loaded — the MCP connection drops when the editor closes and needs the project reopened to come back.

**How to apply:** Before proposing what to port/build next, check the handbook for what milestone/system it specifies, and cross-reference against the live Blueprint state via MCP rather than assuming the handbook's own description of the project is accurate (it was written without opening the editor). Key toolset naming quirks worth knowing before guessing: Behavior Tree inspection is `aimodule_toolset.toolsets.behavior_tree.BehaviorTreeTools` (read-only — no BT graph-writing tool exists via MCP), Blueprint graph surgery is `editor_toolset.toolsets.blueprint.BlueprintTools`, asset-level operations (delete/duplicate/move/find referencers) are `editor_toolset.toolsets.asset.AssetTools`, and generic property get/set on any UObject instance (including Blueprint CDOs) is `editor_toolset.toolsets.object.ObjectTools` (note `set_properties` takes a JSON-encoded string in a `values` param, not a nested object).

**MCP-created assets are memory-only until explicitly saved:** `DataAssetTools.create` / `BlueprintTools.create` (and likely other `*.create` asset tools) create the new asset only in the editor's in-memory transient package -- nothing is written to disk. If the editor is closed/reopened (e.g. for a C++ rebuild) before `AssetTools.save_assets` is called on it, the asset is silently gone with no error, and any later `ObjectTools`/ref-path call against it fails with "is not a valid Object for property". Confirmed by direct repro: created `DA_Chapter_ArchitectureLab`, set its properties, then closed/reopened the editor for an unrelated header fix without saving it first -- `AssetTools.exists` on it returned false afterward. Fix: always call `save_assets` immediately after creating+populating a new asset, before doing anything else that might trigger an editor restart.

**`ObjectTools.set_properties` enforces edit-const, unlike raw C++ reflection:** a `UPROPERTY` needs `EditAnywhere`/`EditDefaultsOnly`/`EditInstanceOnly` for this tool to write it. `VisibleAnywhere` (read-only in the details panel) is silently rejected ("the following properties could not be set: <name>") even though nothing stops a plain C++ `SetValue_InContainer` call from writing it -- the tool deliberately mirrors the editor's own details-panel edit-const check. Relevant when mirroring a handbook illustrative snippet that uses `VisibleAnywhere` for an identity field (e.g. `UUpgradeDefinition`/`UChapterDefinition`'s `ContentId`, described as "set by the content factory") -- until an actual content-factory tool exists to stamp that field some other way, use `EditDefaultsOnly` instead so the field is actually populatable (by a human or by this MCP tooling), matching every sibling field on the class.

**Soft/hard object-reference properties need the full `Package.AssetName` path, not just the package path** when set via `ObjectTools.set_properties` (e.g. a `TSoftObjectPtr<UWorld> Map` field needs `/Game/SOTM/Tests/L_ArchitectureLab.L_ArchitectureLab`, not `/Game/SOTM/Tests/L_ArchitectureLab`) -- same gotcha as the earlier `AssetTools.save_assets` one, generalized to any object-reference property write.

**Native `FGameplayTag` constants shared across modules need a manual `extern MODULE_API` declaration, not the bare `UE_DECLARE_GAMEPLAY_TAG_EXTERN` macro:** that macro expands to plain `extern FNativeGameplayTag TagName;` with no DLL export/import specifier, which will not resolve correctly across a module boundary on Windows (e.g. a tag defined in SOTMCore.cpp and read from SOTMGameplay.cpp). Fix: in the header, write `extern SOTMCORE_API FNativeGameplayTag TAG_Foo;` by hand instead of the macro; keep `UE_DEFINE_GAMEPLAY_TAG(TAG_Foo, "My.Tag")` (no trailing semicolon -- the macro supplies one) in the .cpp as normal. Confirmed working end-to-end this way (`SOTMResultTags.h/.cpp`, `FCommandResult::FailureReason` values read correctly from a different module in a live PIE test). This pattern is also the right choice over `GameplayTagsToolset.AddTag` (which writes `DefaultGameplayTags.ini`, an editor/content change needing user permission per that tool's own docstring) for tags that are pure code constants every command branches on, not designer-authored content -- no permission prompt needed since nothing touches the editor/ini.

**`EditDefaultsOnly` (not `EditAnywhere`) blocks `ObjectTools.set_properties` on a placed/spawned INSTANCE specifically, even though it works fine for reading/writing class defaults:** confirmed via `USOTMMovementPolicyComponent::MovementDefinition` (`EditDefaultsOnly` on a component subobject) -- setting it on a native class placed directly in a level failed with the same "could not be set" error as the earlier `VisibleAnywhere` case, even though `EditDefaultsOnly` properties ARE normally editable (just not per-instance). The tool respects `CPF_DisableEditOnInstance`, not just `CPF_EditConst`/`CPF_Edit`. Fix: configure it on the CLASS DEFAULT OBJECT instead of a live instance -- for a native (non-Blueprint) owning class, this means creating a throwaway Blueprint child (`BlueprintTools.create` with `asset_type` set to the native class's refPath), fetching its CDO (`BlueprintTools.get_default_object`), finding the subobject on that CDO (`ActorTools.get_components(cdo, component_class)`), and `set_properties` on THAT reference -- then place an instance of the Blueprint child (which inherits the configured default) rather than the raw native class.

**Getting a `ULocalPlayerSubsystem` from an arbitrary Actor's Blueprint graph needs the explicit PlayerController-scoped node, not the bare one:** `find_node_types` for a LocalPlayerSubsystem (e.g. `UPresentationSubsystem`) returns two getter node ids -- a bare `LocalPlayerSubsystems|Get<X>` (no input pins) and `PlayerController|LocalPlayerSubsystems|Get<X>` (takes an explicit `PlayerController` input pin). The bare one only resolves a local player from `self`'s own type (PlayerController/Pawn/HUD/PlayerCameraManager) -- called from a plain test `AActor`, it silently returns None (logged as "Accessed None trying to read (real) property CallFunc_GetLocalPlayerSubsystem_ReturnValue in not an UClass" at PIE start, not a graph-build error), and everything chained off it also reads as None/default without crashing. Fix: get a `Game|GetPlayerController` (PlayerIndex 0) first and feed it into the `PlayerController|...` variant explicitly.

**`BlueprintReadOnly` struct fields have no input pin on their auto-generated Make/Set-Members nodes:** confirmed via `get_node_type_pins` on `FWorldStateRecord` (both fields `BlueprintReadOnly`) -- `MakeWorldStateRecord` came back with zero input pins at all, and `SetmembersinWorldStateRecord` exposed only `execute`/`StructRef`/`then`/`StructOut`, no per-field pins -- while `BreakWorldStateRecord` exposed both fields fine as outputs. Reading a `BlueprintReadOnly` struct from Blueprint always works; constructing or mutating one from Blueprint does not, with no error at graph-build time -- the pins are just silently absent. If a test needs to fabricate a struct value with `BlueprintReadOnly` fields, there is no pure-DSL way to do it; either capture a real instance from a native function and round-trip it unmodified, or accept that one code path stays covered by review instead of live PIE.

**A failed physical-overlap PIE test can be the test level's fault, not the collision code under test:** `ASOTMObjectiveMarker`'s trigger (a `USphereComponent` on the "Trigger" profile -- object type WorldDynamic, Pawn response Overlap, confirmed via `ObjectTools.get_properties` on `bodyInstance`) never generated `BeginOverlap` for a `DefaultPawn` swept toward it in `L_ArchitectureLab`, which looked like a collision-profile mismatch and burned significant time theorizing about engine default response tables. The real cause: printing the pawn's actual post-move location (`Transformation|GetActorLocation`, converted via `Utilities|String|ToString(Vector)`) showed it stopped ~95 units into a 500-unit sweep, nowhere near the marker -- it was physically blocked by the test level's sky dome (`StaticMeshActor_1`, mesh `SM_SkySphere` at the origin, scaled 400x), which had `collisionProfileName="BlockAll"` instead of the `NoCollision` a decorative sky mesh should have. Fixed the sky dome's profile via `ObjectTools.set_properties` and re-routed the test pawn's spawn point to approach the marker from nearby instead of sweeping across the whole room; the marker's own collision code needed no further changes and was correct as originally written. **How to apply:** when a live-PIE overlap/movement test doesn't produce the expected event, check the mover's actual final transform *before* re-theorizing about the collision configuration of the actor under test -- unrelated level geometry silently eating the movement is a distinct failure mode from "the two components never agreed to overlap," and the two are easy to conflate without this check. Also useful during the same investigation: `ObjectTools.get_properties` on a live component's `bodyInstance.collisionResponses.responseArray` returns only the entries a profile actually customizes (sparse), not a fully-resolved dense table -- e.g. the "Pawn" profile's array had just one `Visibility` entry -- so it can't be used alone to determine the resolved response for an unlisted channel pair.

**`FTickableGameObject` on a `USubsystem`/UObject silently never ticks unless you explicitly arm it from `Initialize`/`Deinitialize` -- inheriting it is not enough, confirmed by a live PIE false-pass/failure pair:** added `FTickableGameObject` to `UGameFlowSubsystem` (for the terminal-resolution phase, handbook Part 2 section 3.2) with just `Tick`/`GetStatId`/`IsTickable` overridden, the normal-looking pattern. First PIE test result looked plausible (a queued candidate stayed queryable) but was actually a silent no-op: `Tick` was never being called at all, so nothing ever resolved -- caught only because a *second* assertion in the same test (a later call correctly rejected once terminal) failed. `Tickable.h` documents why directly: "Do not use this class with UObjects unless you add explicit code to start and stop ticking... construct with ETickableTickType::Never and call SetTickableTickType to enable ticking later... UObjects are often created and destroyed on background threads so it is not safe to control ticking from the constructor/destructor." Fix: override `GetTickableTickType()` to return `Never`, then call `SetTickableTickType(ETickableTickType::Always)` in `Initialize()` and `SetTickableTickType(ETickableTickType::Never)` in `Deinitialize()` -- confirmed working afterward via the same test. **How to apply:** any future native class that mixes a UObject/USubsystem with `FTickableGameObject` needs this same Initialize/Deinitialize arm-disarm, never bare inheritance -- and don't trust a single passing assertion in a multi-step PIE test as proof the mechanism under test actually ran; a test with only one observable checkpoint can pass for the wrong reason.

**Two UFUNCTIONs sharing the same `Category` + name across sibling classes are ambiguous to `find_node_types`/`write_graph_dsl`, even with a distinct `self` type at the call site:** `ASOTMPlayerState::GetHealthAttributeSet()` and `ASOTMEnemyCharacter::GetHealthAttributeSet()` (both `UFUNCTION(BlueprintPure, Category = "SOTM|Abilities")`) collapsed to one `type_id` ("SOTM|Abilities|GetHealthAttributeSet"). `get_node_type_pins` on it always returned the same one class's overload (whichever it resolves first), and feeding the *other* class's variable into that node's `self` pin via `write_graph_dsl` failed with "Could not connect pin ... to self" -- the tool does not disambiguate by the connected pin's type the way the Blueprint editor's own context-sensitive node picker would. No `context_pins` incantation was found to force the other overload (a guessed `context_pins` entry threw an unrelated internal error). Fix used: sidestep it by testing against only ONE of the two classes (an enemy-vs-enemy damage test instead of enemy-vs-player) rather than fighting the resolver. If both overloads are genuinely needed in the same test graph, give them distinct names or categories instead of relying on this tooling to disambiguate identically-named sibling UFUNCTIONs.

**`write_graph_dsl` gotcha confirmed by direct test (not guessed):** binding a *pure, non-deterministic* node (no exec pins, e.g. `Guid|NewGuid`) once via `(bind x (Node...))` and referencing `x` from two separate exec-sequenced statements does **not** guarantee both reads see the same value — each exec-triggered consumer can re-evaluate the pure node fresh, exactly like the classic "Random Integer wired to two places gives two different numbers" Blueprint gotcha. Confirmed empirically: printing the same `bind`-ed `NewGuid` twice produced two different GUID strings. This produced a false-positive "bug" in a `TryAcceptDeath` de-dup test before the cause was found. Fix: don't reuse a bound pure/non-deterministic call across multiple statements — use a deterministic literal input instead (e.g. `Guid|ParseStringToGuid` with a fixed string, so re-evaluation is harmless), or a real Blueprint variable (Set once via an impure node, Get elsewhere) if a non-deterministic value genuinely needs to be captured once. `add_variable`'s `type_name` also only accepts primitives (`bool, int, float, byte, name, string, text, Vector, Rotator, Transform, Vector2D, LinearColor`) — no `Guid` or other custom structs, confirmed via the tool's own rejection message.

**Two more `SetActorLocation`-in-a-PIE-test movement gotchas, both confirmed by direct instrumentation (print the mover's actual post-move position and compare to the intended target) rather than guessed:**
1. **Always hold the mover's own current Z, never the target object's pivot Z.** A single `SetActorLocation(bSweep=true)` call built from `(X,Y)` of a target actor's `GetActorLocation` plus that SAME actor's own Z (a sphere pickup's Z sits at its radius above ground, a tall box's Z sits mid-height, etc.) drives the moving capsule's center to that mismatched height — embedding it in the floor or floating it above — and the sweep reports a partial, seemingly-arbitrary "blocked" stop well short of the target on the very first attempt, with no explicit collision error. Fix: build the destination as `MakeVector(X=target.X, Y=target.Y, Z=mover's own current Z)` (captured once via `GetActorLocation` on the mover before any moves) for every leg of a multi-stop test, never the target's own Z.
2. **When several `BlockAll`-collision interactables are placed roughly collinearly (a natural layout for a room walked start-to-finish) and a test needs to stand near one to interact without touching its collision, back off *laterally* (perpendicular to the direction of travel), never *longitudinally* (backward along the same bearing).** A longitudinal back-off (e.g. `target.Y - 150` with `target.X` unchanged) leaves the mover directly "upstream" of that object relative to the next waypoint, so the straight-line sweep to the *next* target re-enters the same object's box partway there and stops early or (observed once) appears to not move at all on the next call — confirmed by printing position after every single leg until the exact leg that stalled was identified. A lateral offset (e.g. `target.X - 150`, `target.Y` unchanged, i.e. stepping to the side of the direct path rather than short of it) clears the object without ever re-crossing its footprint on subsequent legs. Confirmed fixing all three affected legs in one M4 end-to-end PIE test after the longitudinal version reproducibly failed twice with different partial-stop numbers.
