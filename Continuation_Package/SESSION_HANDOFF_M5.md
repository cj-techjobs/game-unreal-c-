## Established Unreal MCP / DSL testing methodology

- Toolsets are namespaced; call via `mcp__unreal-mcp__call_tool` with `tool_name` (unqualified, e.g. `load_level`) and `toolset_name` (qualified, e.g. `editor_toolset.toolsets.scene.SceneTools`) as **separate** params — not a single dotted `tool` string. Use `describe_toolset` (param `toolset_name`) to get exact schemas; its output can be huge (gets redirected to a file) — grep/slice that file rather than reading it whole.
- `write_graph_dsl` takes `{graph, code}`. Full DSL grammar reference: call `BlueprintTools.get_graph_dsl_docs` (no params) — returns the complete syntax guide with examples; do this instead of guessing syntax.
- **Critical gotcha confirmed hard this session: `write_graph_dsl`/`add_function_graph`/`compile_blueprint` edits are in-memory only until `AssetTools.save_assets(asset_paths: [])` is called.** A full editor close/reopen (needed for every C++ recompile) silently discards any unsaved Blueprint graph edit, reverting it to whatever was last saved on disk — this bit us directly: a test-driver Blueprint's graph reverted to an old broken version after a C++ rebuild because it had only been compiled, never saved. **Always `save_assets([])` immediately after `compile_blueprint` on anything that needs to survive the next editor restart**, not just at the end of a work session.
- A Blueprint DSL `for` loop containing a latent node (`Utilities|FlowControl|Delay`, or any `WaitX` task) **does not pace in real time** — this is the classic "latent node inside a Blueprint loop macro" limitation (the loop fires all N iterations' bodies without waiting for each Delay to actually complete). Confirmed directly: a 15-iteration attack-test loop with a 1.2s Delay per iteration printed its start and completion log lines at the *same* timestamp. **Workaround used successfully**: don't loop at all — either unroll a flat sequential chain of `(Delay N) (stmts...)` pairs (a single, non-loop Delay chain *does* pace correctly), or better, use `Utilities|Time|SetTimerbyFunctionName` with `:bLooping true` calling a small custom `(fn ...)` graph — this reliably fires on a real-time interval and was used to confirm `RemainingLives` polling every 3s across a 30+ second PIE session with exact real-world timestamps.
- A custom Blueprint function added via `add_function_graph` cannot be called from DSL by guessing a node type ID (e.g. `SOTM|FunctionName` does not work) — calling it via a `SetTimerbyFunctionName` (by string name) does work and was the workaround used.
- Setting `bodyInstance.collisionEnabled` directly via `ObjectTools.set_properties` does **not** persist if `collisionProfileName` remains a named (non-Custom) profile — the profile reasserts its own collision state at spawn/registration. Set `collisionProfileName` itself instead (e.g. to the built-in `"NoCollision"` profile) — this was the actual fix for a gate whose collision wouldn't disable.
- `UProjectileMovementComponent::bSweepCollision` defaults `false` — a fast projectile will tunnel through targets with no collision event unless this is set `true` explicitly in the constructor.
- `ObjectTools.get_properties` reflection reads can be stale/wrong for some live-simulation values (confirmed via direct `UE_LOG` cross-check on `MaxWalkSpeed`) — a tool-side quirk; cross-check via logs if a read looks implausible. `ObjectTools.list_properties` is the reliable way to discover **exact** property names before calling `get_properties`/`set_properties` — don't guess casing (properties are lowerCamelCase in this API regardless of the C++ UPROPERTY's PascalCase name, e.g. `attackDamage`, `staminaDrainPerSecond`).
- To inspect a live PIE actor by class: `SceneTools.find_actors` with `actor_type: {refPath: "/Game/Path/BP_Foo.BP_Foo_C"}` (Blueprint classes) or `{refPath: "/Script/ModuleName.ANativeClass"}` (native classes, e.g. AI controllers) against the **PIE world's** level path (`.../UEDPIE_0_L_LevelName.L_LevelName:PersistentLevel.ActorName_0`), not the editor-world path.
- `aimodule_toolset.toolsets.behavior_tree.BehaviorTreeTools` (`list_nodes`, `get_children`, `get_root_decorators`) can inspect an existing `.uasset` Behavior Tree's structure read-only — **always check this before assuming a BT capability is missing**; see the enemy-attack postmortem below, where an entire pre-built Chase→Attack branch with native C++ task backing (`BTTask_SOTMChasePlayer`, `BTTask_SOTMAttackPlayer`) was initially missed.
- Established PIE-verification loop: edit → compile → **save_assets([])** → tell user to recompile if C++ → `list_toolsets` (confirms MCP reconnect) → `load_level` → `StartPIE` → `GetLogEntries`/`GetAttributeValues`/`get_properties` to inspect → `StopPIE` → delete scaffolding → `save_assets([])`.

### Real bugs found via hands-on playtesting this session, and fixes (chronological)

1. **No on-screen feedback for pickups/interaction at all** — user couldn't tell if a pickup registered or what "press E" prompt was active. Fixed with `AddOnScreenDebugMessage` calls in `SOTMCurrencyPickup.cpp`, `SOTMKeyPickup.cpp`, `SOTMInteractionComponent.cpp`.
2. **Gate collision never disabled after opening** — a separately-added visual mesh component had its own untouched collision. Root-caused to the `collisionProfileName` vs `collisionEnabled` gotcha above; fixed by setting the profile itself.
3. **`UProgressionSubsystem::StartNewRun()` was never called anywhere** — confirmed via `Grep` across the whole codebase. A fresh run's `RemainingLives` sat at the raw struct default (0), which would silently turn the very first accepted death into an instant GameOver instead of a normal retry (no GameOver UI exists either, so this would have looked like "nothing happens"). **Fixed** in `ASOTMChapterGameMode::BeginPlay()`: calls `Progression->StartNewRun()` if `!Progression->GetSnapshot().RunId.IsValid()`. PIE-confirmed via a repeating-timer status print: `RemainingLives` reads `5` from the first tick and holds steady.
4. **Enemy never actually killed the player — full postmortem, includes a fix that was built, then correctly reverted.**
   - Initial (wrong) diagnosis: assumed nothing ever called `ASOTMEnemyCharacter::AttackPlayer()`, based on reading only `ASOTMAIController`'s C++ — missed that `BT_AI` (a Behavior Tree **asset**, not C++) already had a fully-wired `BTComposite_Selector` → (`seeingPlayer`-gated) `BTComposite_Sequence` → `BTTask_SOTMChasePlayer` → `BTTask_SOTMAttackPlayer` branch, with native C++ backing for both tasks already in the codebase (`BTTask_SOTMChasePlayer.cpp`/`BTTask_SOTMAttackPlayer.cpp`), calling `Enemy->AttackPlayer()` directly. **Lesson recorded**: before concluding an AI capability is "missing" and adding a controller-level substitute, inspect the actual `.uasset` Behavior Tree via `BehaviorTreeTools.list_nodes`/`get_children` — don't infer tree content from the controller's C++ alone.
   - Built (then reverted): a new `ISOTMMeleeAttacker` interface + `ASOTMAIController::TryAttackCurrentTarget()` (called every `Tick()`) as a parallel attack-trigger, plus a snap-to-face-target fix. This did make damage land in a scripted test — but only because it papered over the *real* bug below with a second, independent (and face-correcting) code path. The user's own hands-on retest confirmed the real BT-driven path works fine and asked to revert the parallel mechanism: *"revert the changes you did earlier for these bugs (those were actually not the issues at all)."* **Reverted in full**: deleted `SOTMMeleeAttacker.h`, removed the interface from `ASOTMEnemyCharacter`, removed `TryAttackCurrentTarget`/`AttackRange`/`AttackCooldownSeconds`/`NextAttackAllowedTime` from `ASOTMAIController`.
   - **Actual root cause**: `BTTask_SOTMChasePlayer`'s `AcceptanceRadius` (120) was larger than the attack's actual reach (`AttackTraceDistance` 70 + `AttackTraceRadius` 25 ≈ 95) — the enemy stopped chasing *before* it was close enough for its own attack trace to connect. A real, permanent, minimal fix: `BTTask_SOTMChasePlayer_0.AcceptanceRadius` 120→**80** (data-only, in `BT_AI.uasset`) and `ASOTMEnemyCharacter::AttackTraceDistance` 70→**120** (C++ default). PIE- and user-confirmed working after this.
5. **Sprint stopped after ~2-3 seconds even with no Speed Boost involved** — user initially suspected a Speed-Boost interaction (a real earlier ask, "decouple this ability logic from walk/sprint," had already been addressed by removing a redundant `FInterpTo` easing layer on `MaxWalkSpeed` in `USOTMMovementPolicyComponent::TickComponent` — that change is correct and was **kept**, not reverted). The actual, separate cause: plain stamina drain (`StaminaDrainPerSecond=20` against `MaxStamina=100`) latching sprint off once exhausted. User's explicit direction: *"make sure there is no stamina or so, as long as I'm holding sprint input it should keep sprinting."* **Fixed**: `StaminaDrainPerSecond` set to `0` both on `DA_MovementDefinition_Default` (data) and as the new C++ class default in `MovementDefinition.h` — the stamina *system* is left intact in code (drain/recovery/exhaustion-latch logic untouched) in case it's wanted again later; only the drain rate was neutralized. Acceleration tuning (2048→3000, from an earlier "reach max speed in ≤0.5s" ask) was **kept**, not reverted.
6. **Forward/backward movement capped noticeably below max speed (e.g. 264 instead of 300 in Walk), but strafing (A/D) reached full speed.** Root cause: `ASOTMPlayerCharacter::HandleMove()` built its direction vectors from `FRotationMatrix(GetControlRotation())` — the **full** control rotation, pitch included. The forward axis of that rotation tilts with camera pitch, so its horizontal component (and therefore ground speed) shrinks to `cos(pitch)` of input magnitude; the right axis of the same rotation stays horizontal regardless of pitch (pitch rotates about the right axis), which is exactly why only forward/back was affected. `264/300 ≈ 0.88 ≈ cos(28°)`, a plausible camera pitch. **Fixed**: build the rotation matrix from `FRotator(0, GetControlRotation().Yaw, 0)` (yaw only) instead. User-confirmed working after this — **this was the last item; user reported "everything's working fine now."**
